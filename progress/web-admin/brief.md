# web-admin (fase 3: panel `/admin` en `cv-web`)

Decisiones del humano (ya tomadas, no se reabren): el panel vive en `cv-web` (servidor Next standalone en el NAS) y llama a la API **solo desde su propio servidor** (route handlers; cookie httpOnly; el navegador no habla con los endpoints admin); modelo de login de `fion-gastronomy` (login por route handler → JWT en cookie httpOnly, `proxy.ts` como puerta, backend valida cada llamada, panel `noindex`); un único administrador, solo contraseña; ABM en tiempo real sin rebuild (la web pública ya lee sin caché y la API invalida su caché al guardar); si la API cae, la web cae; la web pública se publica en `floreslab.dev`.
Contrato de la API ya implementado y APROBADO (repo `cv`, plan en `progress/api-admin/analysis.md` §4 y §10, documentación en `docs/admin-runbook.md` y el Swagger): `POST /api/v1/admin/auth/login`, `GET /auth/session`, `PUT /auth/password`, `POST /auth/logout-all`; `GET/PUT /api/v1/admin/content/{services|projects|architecture}` (documento completo ES+EN, `baseVersions`, 409 `CONTENT_VERSION_CONFLICT`, 422 `CONTENT_INVALID` con `errors:[{path,code}]`, 422 `CONTENT_PARITY_BROKEN`), `GET .../content/{kind}/{lang}/versions[/{n}]`, `POST .../rollback`; `POST/GET/DELETE /api/v1/admin/images`, `POST /images/cleanup`; `GET /api/v1/admin/contact-messages`. Todas las respuestas admin llevan `Cache-Control: no-store`. La API acepta `X-Request-Id` (la web debe generarlo/propagarlo) y registra la IP del cliente en las rutas admin desde `CF-Connecting-IP` o, si falta, `X-Client-IP`: **el panel debe enviar `X-Client-IP` con la IP del navegador** (tomada de `CF-Connecting-IP` de la petición entrante a la web) y **NUNCA reenviar cabeceras `CF-*`** a la API (rompería el `AdminEdgeGuard`, que responde 404 a toda petición admin con `CF-Ray`/`CF-Connecting-IP` cuando `CV_ADMIN_EDGE_BLOCK=true`, que es lo configurado en producción). La web ya tiene `lib/log.ts` (única salida de logs), `lib/api/request.ts` (transporte `node:http`, `X-Request-Id`), `instrumentation.ts`, diseño v2 (tokens plano/obra, Barlow Condensed/IBM Plex), i18n ES/EN y tests de runtime sobre el standalone.
Alcance deseado (el plan lo concreta y lo discute en Riesgos):
1. **Autenticación y sesión:** `/admin/login` (solo contraseña, errores genéricos, 429 con `Retry-After`), cookie httpOnly `Secure` `SameSite=Strict` `Path=/admin` (comprobar con el túnel/HTTP en local), `proxy.ts` (único; matcher `/admin/:path*`; solo comprueba la presencia de la cookie: la autoridad es la API), `noindex`/`robots`, caducidad/401 → login, cerrar sesión, cambio de contraseña (`PUT /auth/password` renueva la cookie con el token nuevo), «cerrar todas las sesiones», protección CSRF (comprobar `Origin`/`Sec-Fetch-Site` en handlers que mutan).
2. **Edición de contenido** de servicios, proyectos y arquitectura (hexágono: núcleo, puertos, adaptadores con `status`) con ES y EN en la misma pantalla, validación en cliente que refleje la del API y errores del servidor mapeados por `path` a campos, control de versión optimista (409 → «alguien cambió esto», recargar sin perder lo escrito), vista de paridad ES/EN, historial de versiones y rollback con confirmación, comentario del guardado, avisos de privacidad (un proyecto `anonymous` no admite cliente; solo proyectos `own`+`public` admiten imágenes).
3. **Imágenes:** subida (arrastrar/seleccionar; tipos y tamaño comprobados antes de enviar), selector de portada y orden por proyecto, `alt` ES/EN, vista previa, listado de imágenes con «en uso» y borrado (409 si referenciada por cualquier versión), limpieza de huérfanas con simulación previa.
4. **Mensajes de contacto:** lista paginada de solo lectura.
5. **Web pública:** tipos TS de `images[]` en `lib/api/types.ts` (regenerar desde el OpenAPI de la API) y que la web pública lea `project.images[0].url` (portada) en lugar de `public/projects/<id>.webp`, manteniendo `canShowImage` y los estados vacíos.
6. **Observabilidad:** logs del panel por `lib/log.ts` (login ok/fallido/bloqueado sin datos, guardados, subidas) con `request_id`, sin contraseñas, tokens, cuerpos ni IP en claro más allá de lo que ya hace la API.
7. **Calidad:** accesibilidad (teclado, foco, etiquetas, errores anunciados), responsive (móvil y escritorio), diseño coherente con v2 (reutilizar tokens y componentes; sin librería de UI nueva salvo justificación en el plan), tests de componentes, de route handlers y de runtime sobre el standalone con una API falsa que implemente el contrato admin (ampliar `scripts/parity/design-api.mjs`/`tests/helpers/fake-api.ts` sin duplicar), verificación visual con Chrome DevTools (hoy el MCP `chrome-devtools` está desconectado: el plan debe indicar qué verificaciones visuales requieren reconectarlo).
Riesgos/dudas que el plan debe resolver o llevar a Riesgos con recomendación: UX de edición de proyectos (lista + formulario vs. todo en una pantalla), editor del hexágono (formularios vs. JSON), edición en pares ES/EN (lado a lado vs. pestañas), manejo de borradores sin guardar y pérdida de datos en 409, tamaño de subida y límites de Next route handlers en el standalone (5 MB), cookie `Secure` tras el túnel de Cloudflare (HTTP interno), `X-Client-IP` y la IP real (`CF-Connecting-IP` de la petición entrante), CSRF, rate limiting del login ya lo hace la API (por cuenta), compatibilidad con el `proxy.ts` y con el log de peticiones, y cómo se prueba sin la API real.
Fuera de alcance: roles/usuarios múltiples, edición del CV (`resume`), métricas, WebSocket.

## Decisiones validadas (2026-11-13)
Julio dio el visto bueno al plan y aceptó las recomendaciones: (1) errores con texto+icono+borde grueso, sin token nuevo; (2) panel solo en español; (3) `Disallow: /admin/` + noindex; (4) ids existentes de solo lectura; (5) cookie SameSite=Strict; (6) límite de intentos en Cloudflare = tarea del humano. Orden de slugs: web-admin-api-client → auth → content-core → projects → architecture → images → public-images → history → messages → regresion. Sin cerrar hasta "cerrá". chrome-devtools MCP reconectado.
Cambio de decisión (2026-11-14, aprobado por Julio en la review de `web-admin-images`, opción a): el matcher de `proxy.ts` deja fuera `/admin/api/images` y sus subrutas (`['/admin', '/admin/((?!api/images(?:/|$)).*)']`). Con el proxy delante, Next leía el cuerpo entero de la subida antes del handler (el 413 llegaba al terminar de enviar y por encima de 10 MB escribía una línea no JSON). Esos handlers exigen la sesión ellos mismos (401 sin cookie), comprueban CSRF y responden `no-store`; las cabeceras del panel siguen saliendo de `next.config.ts`.
Cambio de decisión (2026-11-14, aprobado por Julio en la review de `web-admin-public-images`): la web pública solo muestra una portada si su URL es `https:` absoluta (sin credenciales); una `http:` plana o cualquier otra se descarta, sin caer a la segunda imagen. No se fija el dominio de medios ni se añade CSP (la web confía en la URL que compone la API).
