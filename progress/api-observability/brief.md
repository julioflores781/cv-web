# api-observability (repo `cv`, y su contraparte en `cv-web`)

Petición del humano (2026-11-12): «la API no está logueando nada; cada endpoint debería mostrar que alguien llamó; deberíamos tener algo de observabilidad; por las pruebas no veo que se deje nada en log».
Estado comprobado en `cv`: sin ninguna configuración de logging ni access log en `application.properties`; solo unos pocos logs ad hoc (`AdminConfig`, `PostgresSiteContentRepository`, `PostgresResumeRepository`, `TelegramContactNotifier`, `ProblemExceptionMapper`, `RollbackContentService`, `SaveEditableContentService`); solo `quarkus-smallrye-health` (sin métricas ni trazas). Las pruebas no verifican logs. Despliegue: contenedor en un NAS, logs con `docker logs`/Portainer; la API es pública (Cloudflare Tunnel, cabeceras `CF-Connecting-IP`), `cv-web` la llama por red interna.
Propuesta del leader (recomendaciones, el humano las valida con el plan):
1. **Access log**: una línea por petición (método, ruta sin query sensible, estado, duración, tamaño, request id); excluir ruido (health checks cada 30 s, swagger/estáticos).
2. **Request id**: aceptar/propagar `X-Request-Id` (lo enviará `cv-web`), generarlo si falta, devolverlo en la respuesta, ponerlo en el MDC y en los problem+json para correlacionar.
3. **Logs JSON en producción** (MDC como campos) y texto legible en dev/test.
4. **Auditoría del admin** (categoría de log propia `audit`): login ok/fallo/bloqueado, cambio de contraseña, logout-all, guardado de contenido (tipo, versiones, comentario), rollback, subida/borrado/limpieza de imágenes, lectura de mensajes; con IP del cliente (`CF-Connecting-IP`) SOLO en las rutas admin (útil para detectar fuerza bruta). Nunca cuerpos, contraseñas, tokens, cabecera Authorization, contenido de mensajes de contacto, nombres de cliente.
5. **Eventos de negocio INFO**: mensaje de contacto recibido (solo id), resultado de la notificación de Telegram, invalidaciones de caché, fallos de refresco de BD (WARN existentes).
6. **Privacidad**: en los endpoints públicos NO se registra IP (la web ya hashea la IP con sal para el límite de contacto); decisión del humano pendiente.
7. **Métricas**: opcional/posterior (Micrometer/Prometheus en interfaz de gestión interna no publicada, sin tocar la ruta de health que usan el compose y `cv-web`); decisión del humano pendiente.
8. **Pruebas**: las nuevas pruebas capturan los logs y afirman (a) que se emite la línea esperada para cada endpoint y evento de auditoría y (b) que NUNCA aparecen datos sensibles (contraseña, token, hash, Authorization, cuerpo de mensajes, IP en públicos).
9. **Contraparte en `cv-web`** (servidor Next standalone): log de peticiones propias de la web (rutas `/api/health`, `/api/contact`, PDF y errores 500 con causa sin datos sensibles), generar/propagar `X-Request-Id` hacia la API (lectura y contacto), formato coherente con la API.
Decisiones tomadas por el humano que NO se reabren: arquitectura hexagonal del repo `cv` (capas, ArchUnit), repo público sin secretos, nada de datos personales en logs. Documentar dónde leer los logs en el NAS (Portainer/`docker logs`) y cómo buscar por request id.
Preguntas para el plan: ¿extensión de Quarkus para JSON (`quarkus-logging-json`) y compatibilidad con la imagen y el cableado actual?; ¿cómo hacer el access log (`quarkus.http.access-log` con patrón propio o un `ContainerRequest/ResponseFilter` propio) para controlar qué se registra y excluir rutas?; ¿cómo propagar el request id al MDC también en hilos de trabajo?; ¿cómo capturar logs en pruebas (`LogCapture`/handler propio)?; ¿rotación/volumen de logs en el NAS?; ¿cómo evitar registrar el query string con datos?
