# api-admin (fase 2: ABM + admin + imágenes en R2) — repo `cv`

Decisiones del humano (Julio), ya tomadas, no se reabren:
1. **Un único administrador.** Su contraseña vive **en la base de datos, hasheada** (bcrypt o argon2; nunca en variables de entorno ni en el repo). Sin contraseña por defecto sembrada; la primera se crea con un script/comando en el NAS; se puede cambiar rápido si se pierde (script en el NAS) y también desde el panel con la contraseña actual. Cambiar la contraseña invalida las sesiones. Login con límite de intentos (anti fuerza bruta).
   Modelo de referencia (simple, sin IAM completo): `repo fion-gastronomy` (login → JWT, el front lo guarda en cookie httpOnly, el backend valida el JWT en cada llamada, throttle 5/min). NO usar el IAM de `repo padelhub-api` (usuarios, roles, refresh, Google).
2. **ABM en tiempo real, sin rebuild.** CRUD de **servicios, proyectos y arquitectura** (el hexágono: núcleo, puertos, adaptadores) sobre `content_version` (JSONB versionado, instantáneas inmutables, una activa por tipo e idioma, ya existe: migración V3). Cada guardado crea una versión nueva, con historial, vuelta atrás (rollback) y control de concurrencia optimista. Mantener ES/EN con la misma estructura. Los proyectos `anonymous` nunca guardan nombre de cliente (regla ya existente del dominio y de `make-seed.py`). Al guardar, la API debe **invalidar su propia caché de contenido** (`cv.content.cache-ttl`, 5 min; y la del CV `cv.resume.cache-ttl` si el ABM tocara el CV) para que la web (que ya lee sin caché) lo vea al instante.
3. **Imágenes de proyectos en Cloudflare R2**, como en `padelhub-api` (`src/media`: puerto `FileStoragePort` + adaptador `R2FileStorageAdapter` con cliente S3, variables `R2_ACCESS_KEY_ID/R2_SECRET_ACCESS_KEY/R2_ENDPOINT/R2_BUCKET_NAME/R2_PUBLIC_URL`, subida multipart, 5 MB, jpeg/png/webp/gif, URL pública). Se **reutiliza el mismo bucket y `https://media.floreslab.dev`**, con prefijo `site/`. Las imágenes se asocian a proyectos (hoy la web las busca en `public/projects/<id>.webp`: el plan debe definir el campo `images`/portada en el JSON del proyecto y cómo la web lo consumirá en la fase 3).
4. **Arquitectura del repo `cv`:** hexagonal (dominio y aplicación sin frameworks; ArchUnit lo impone), un caso de uso = una interfaz de entrada, cableado solo en `UseCaseConfig`, errores con código estable y mensajes ES/EN en `problems_*.properties`, Swagger completo con ejemplos (OpenApiDocumentTest), cobertura ≥90 % total y ≥80 % por módulo, pruebas con Testcontainers. Commits en inglés, sin atribución. Repo público: nada de secretos ni datos reales; las pruebas usan el CV ficticio (Ada Ejemplo).
5. **Consumo:** el panel `/admin` (fase 3) vive en `cv-web` y llama a la API **desde su propio servidor** (route handlers, cookie httpOnly): el navegador no habla con los endpoints admin. La API es pública (`cv-api.floreslab.dev`, con Swagger): el plan debe analizar cómo proteger bien `/api/v1/admin/*` (JWT, límites, y si conviene bloquearlo o restringirlo en el túnel/Cloudflare) y qué ve Swagger.
6. Despliegue: compose único del NAS en `cv-web/deploy/docker-compose.yml` (añadir las `R2_*` y lo que haga falta); imagen `julioflores781/cv-api` por CI de `cv` al fusionar a `main`.

Fuera de alcance: UI del panel (fase 3, repo `cv-web`), WebSocket (descartado), usuarios múltiples/roles, edición del CV (`resume`) desde el panel salvo que el analista lo justifique como riesgo/duda.
Preguntas que el plan debe resolver o llevar a Riesgos: ¿editar el documento completo por tipo e idioma o items sueltos?; ¿leer mensajes de contacto desde el admin?; ¿JWT con SmallRye (Quarkus) y cómo invalidar sesiones al cambiar la contraseña (versión de token)?; ¿bcrypt vs argon2 en Quarkus/Java 21?; ¿cliente S3 (AWS SDK v2 / extensión `quarkus-amazon-s3`) con endpoint de R2?; borrado de imágenes huérfanas; validación real del tipo de imagen (bytes mágicos), tamaño, nombres.
