## 0. Lo verificado (no inventado)

### Repo de la API (repo `cv`, HEAD `d5e0a4a`, 2026-11-04)
- **Pruebas: 127.** Contadas de dos formas que coinciden: `@Test`/`@ParameterizedTest` en `src/test` (domain 15, application 17, infrastructure 95) y `python3 scripts/ci-summary.py` tras el `target/` existente: "127 de 127 pruebas pasan".
- **Cobertura de líneas: 95,8 %** (600/626). Por módulo: application 100 % (91/91), domain 84,0 % (63/75), infrastructure 97,0 % (446/460). Ramas 83,7 %. Umbrales impuestos por CI: **90 % total y 80 % por módulo** (`ci-summary.py --min-total 90 --min-module 80`). El brief decía "~95 %": la cifra real es 95,8 %; en la web se escribe "95,8 %" (ES) / "95.8%" (EN), no "≈95".
- **Endpoints implementados** (coinciden el `openapi.json` vivo, consultado con `curl` el 2026-11-04, y el código): `GET /api/v1/{profile,impact,experience,experience/{id},skills,education,contact,resume}` y `POST /api/v1/hl7/translate?format=json|fhir`. **Son 9 operaciones (8 GET + 1 POST).** Fuera del prefijo: `/openapi.json`, `/swagger/`, `/q/health/{live,ready}`.
- **NO implementados aún** aunque `ARCHITECTURE.md` los lista como diseño: `/resume.pdf`, `/status`, `POST /contact/messages`, `/llms.txt`, `?format=jsonresume`, ETag, `contact_message`, `page_view_daily`. **La web no debe presentarlos como existentes** (como mucho, "próximamente" en una línea o nada; ver D1).
- **Módulos Maven: 3** (`domain`, `application`, `infrastructure`). `domain` 16 clases (Resume agregado, Profile, WorkExperience, Phase, SkillGroup, Impact, Education, Period…). `application`: **8 casos de uso** (puertos de entrada `Get{Profile,Impact,Experience,Skills,Education,Contact,Resume}UseCase` + `TranslateHl7UseCase`) y **2 puertos de salida** (`ResumeRepository`, `Hl7Translator`). `infrastructure`: adaptadores `adapter/in/rest` (+ `error`), `adapter/out/postgres`, `adapter/out/hl7`, y `config/UseCaseConfig` (único cableado). Los puertos `Mailer`, `RateLimiter`, `ResumeRenderer`… de `ARCHITECTURE.md` **no existen todavía**: no dibujarlos.
- **ArchUnit:** `ArchitectureTest` tiene 9 `@Test` (1 de sanidad que comprueba que analiza clases de los tres módulos + 8 reglas): dominio no depende de otras capas, dominio sin frameworks, aplicación solo conoce el dominio, adaptadores de entrada y de salida no se importan entre sí, toda excepción de negocio extiende `ApplicationException`, solo el paquete `error` mapea excepciones a HTTP, solo `error` contiene el texto de errores. Usa la API principal de ArchUnit (el módulo `archunit-junit5` 1.5.1 no funciona con JUnit 6 de Quarkus 3.40).
- **Datos:** PostgreSQL, tabla `resume_version` (JSONB, una fila por versión e idioma, flag `active`). Flyway crea el esquema al arrancar. Publicar = `scripts/make-seed.py` genera SQL (desactiva la activa e inserta la siguiente) y se aplica con `psql`; **rollback** con `make-seed.py --rollback <lang>`. La API cachea en memoria 5 min (`cv.resume.cache-ttl=PT5M`), un CV no encontrado 10 s, y si la BD falla al refrescar sirve el último CV leído. Contenido real fuera del repo (`private/`, ignorado por git); pruebas y CI usan el CV ficticio `db/sample` (Ada Ejemplo).
- **Errores:** RFC 7807 (`application/problem+json`) con `type,title,status,detail,code`; `code` estable e independiente del idioma; `title/detail` en el idioma de la petición (`?lang` > `Accept-Language` > `es`). `ProblemCatalogTest` falla si falta un texto. i18n acotado: solo contenido y mensajes de error (no Swagger ni logs).
- **Caché HTTP / CORS:** `Cache-Control: public, max-age=300` + `Vary: Accept-Language` en los 200; CORS limitado al dominio de la web (configurable por `QUARKUS_HTTP_CORS_ORIGINS`).
- **HL7:** solo v2.5.1, `ADT^A01` y `ORU^R01`, HAPI, mapeo manual a FHIR R4 (PID→Patient, PV1→Encounter, OBX→Observation); máx. 64 KB, el cuerpo no se guarda ni se registra, solo mensajes sintéticos. (Detalle de la demo = tarea `web-hl7-demo`; aquí solo se menciona como decisión.)
- **CI (`.github/workflows/ci.yml`), dos trabajos:** (1) *Pruebas y cobertura* en cada push y PR: `mvn -B verify`, `ci-summary.py` con umbrales, informes como artefacto 14 días; en push sube el artefacto `quarkus-app`. (2) *Imagen Docker*, solo en push a `main` o tag `v*` y `needs: test`: descarga **el mismo artefacto probado**, construye amd64, levanta un PostgreSQL desechable con el CV ficticio, ejecuta `scripts/smoke-test.sh` (readiness, endpoints, errores 404 con código estable, HL7) y **solo si pasa** publica `linux/amd64` + `linux/arm64` en Docker Hub (`julioflores781/cv-api`; tags `latest`, `sha-<corto>`, `X.Y.Z`, `X.Y`). **No hay despliegue automático al servidor**: el `docker-compose.yml` se pega en el NAS y la imagen se baja a mano. La publicación del CV tampoco está automatizada (psql manual).
- **Red:** `deploy/docker-compose.yml`: `cv-db` sin puertos publicados (solo la API llega a la BD); `cv-api` sin puertos publicados, alcanzada por Cloudflare Tunnel (`cloudflared` ya existente) por nombre de servicio. Estos nombres/redes **no se publican** en la web.
- **Repo público:** `origin = https://github.com/julioflores781/cv-as-a-service.git` (coincide con el brief). `cv-web` sin remoto: no enlazar.

### Repo de la web (`cv-web`)
- Next 16.4.5, React 19.3.1, `output:'export'`, `trailingSlash:true`. Una sola ruta `app/[[...lang]]/page.tsx` con `generateStaticParams` fijo `[{lang:[]},{lang:['en']}]`, `dynamicParams=false`; `resolveLang` hace `notFound()` si no es `[]` o `['en']`. El layout `app/[[...lang]]/layout.tsx` fija `<html lang>` con `lang[0]` (si no es un idioma válido cae a `es`).

Tokens en `app/globals.css :root` (`--bg --surface --ink --muted --line --accent --accent-ink --soft --pill-line --font --head --mono --radius`). Tests de build (`tests/build/build.test.ts`) ejecutan un `next build` real contra una API falsa con "Ada Ejemplo".

## 8. Alternativa descartada
1. **Carpetas de ruta separadas** (`app/arquitectura/page.tsx` y `app/en/architecture/page.tsx`). Descartada: el layout raíz (`<html lang>`, tokens, `globals.css`) vive en `app/[[...lang]]/` y habría que duplicarlo o reestructurar con *route groups*; además un catch-all opcional con carpetas estáticas hermanas hace menos obvia la precedencia de rutas, y el sitemap/hreflang/selector de idioma quedarían repartidos. Elegido: ampliar `[[...lang]]` con una tabla de rutas (`lib/i18n/routes.ts`) como única fuente de verdad para `generateStaticParams`, `resolveRoute`, `pagePath`, sitemap, hreflang y selector de idioma. Coste: un `resolveRoute` más general que el `resolveLang` actual.
2. **Diagramas como imágenes** (SVG/PNG en `public/` o Mermaid renderizado en cliente). Descartada: no heredan tokens ni tema, no tienen texto real accesible/traducible por idioma (habría dos imágenes por diagrama), añaden dependencias o JS de cliente y dificultan los tests de contenido. Elegido: SVG en línea como componentes React puros con contenido por props.
3. **Diagrama único gigante** de flujo + CI/CD + hexagonal. Descartada: ilegible a 360 px y mezcla tres historias (cómo se sirve, cómo se publica, cómo está hecha la API). Elegido: tres diagramas con un mensaje cada uno.
4. **Contenido en la API** (la arquitectura vendría de `/api/v1/...`): fuera de decisión del brief (contenido estático en diccionarios).

## 9. Riesgos / dudas
- **R1 — Rutas bilingües, sitemap y hreflang (resuelto en el diseño, a validar).** `/arquitectura/` = segmentos `['arquitectura']` y `/en/architecture/` = `['en','architecture']` dentro de `[[...lang]]`; no hay un segmento común con el idioma, por eso **no se puede deducir el idioma solo de `lang[0]`** y el layout debe usar `resolveRoute`. Reglas: (1) cada URL es canónica de sí misma (autorreferencia); (2) el hreflang de una página enlaza a **su traducción** (arquitectura↔arquitectura, nunca a la home), reciprocidad completa y `x-default`→ES de esa misma página; (3) el sitemap lista las 4 URLs con `alternates` por página; (4) barra final en todas (`trailingSlash:true`); (5) la home mantiene su hreflang actual. Pendiente: confirmar en Pages (`web-deploy`) que `/arquitectura` sin barra redirige a `/arquitectura/` (hoy ya pendiente para `/en` → `/en/`, ver `progress/web-home/impl.md`). Duda para el humano: ¿el slug ES se escribe sin tilde (`arquitectura`)? Es el que ponía el brief; sin tilde evita URLs con percent-encoding.
- **R2 — Build hook y "publicación → web nueva".** El brief dibuja `seed SQL → PostgreSQL → build hook → web nueva`, pero **hoy no existe ningún hook** (`web-deploy` está sin hacer, y publicar el CV es un `psql` manual que no dispara nada). Dibujarlo como automático sería afirmar algo falso. Propuesta por defecto: dibujarlo y rotularlo "tras publicar, se dispara un build (deploy hook de Pages)" **solo si `web-deploy` lo deja operativo antes de cerrar esta tarea**; si no, el implementer lo dibuja como paso manual ("reconstruir la web") o en discontinuo "siguiente paso", y T18 se ajusta. **Decisión del humano.** Mismo caso para "Despliegue manual" (D2) si algún día se automatiza.

Requiere revisión visual del reviewer (captura a 360 y a escritorio) y, si el repo adopta Playwright más adelante, un test visual. Se fija `min-width` del SVG (≈640 px) como mitigación; si el humano prefiere reflujo vertical en móvil (versión apilada del diagrama), es otro diseño y más trabajo.
