# web-logging

Slug hijo 4 de `api-observability`, esta vez en el repo **`cv-web`** (servidor Next standalone, Node 22 con nvm: el node por defecto es 20 y rompe los tests de PDF). La API (`cv`) ya acepta, valida y devuelve `X-Request-Id` (`api-logging-core`, APPROVED y sin cerrar) y registra el contacto, Telegram y la invalidación (`api-business-events`, APPROVED y sin cerrar): este slug es su contraparte web.
Plan validado por el humano: `progress/api-observability/analysis.md` (**§2.7 lado web, §3 archivos de `cv-web`, §4.4 campos y ejemplos de línea, §5 A13–A14, §6.4 tests W1–W21, §7 privacidad, §9 alternativas (no `proxy.ts`), §10 R12**, §11 «Orden 4»).
Decisiones del humano (no se reabren): ninguna IP ni dato del formulario en los logs web; no se usa `proxy.ts` (reservado para la fase 3 del panel); sin log por visita de página (el standalone no da un hook con estado y duración sin `proxy.ts`; las visitas se ven en el access log de la API y en Cloudflare); las lecturas correctas a la API son SILENCIOSAS (la API ya registra cada lectura); `console.*` solo dentro de `lib/log.ts`.
Alcance: `lib/log.ts` (`logEvent(level, event, fields)`: una línea JSON por stdout (info) o stderr (warn/error) con `timestamp`, `level`, `service:"cv-web"`, `event`, `request_id` y campos primitivos; descarta objetos/funciones/circulares, convierte `Error` en nombre de clase, sanea saltos de línea/comillas y trunca; lista negra de claves `password, token, authorization, cookie, email, message, name, ip, body, website`; nunca lanza); `lib/request-id.ts` (32 hex); `lib/api/request.ts` (un id por `requestJson` enviado en `X-Request-Id`, el mismo en los reintentos; WARN por intento fallido con `event=api_call`, `path` sin query, `status`/`outcome` (http_error, timeout, unreachable, invalid_response), `attempt`, `duration_ms`, sin host ni cuerpo ni causa con URL); `lib/api/health.ts` (id); `lib/api/contact.ts` (acepta `requestId` y lo manda en `X-Request-Id`, sigue sin reenviar nada más que `Content-Type` y la IP válida); `app/api/contact/route.ts` (un id por POST, un INFO `event=contact` con `outcome`, `status`, `code`/`reason` sin valores, cabecera de respuesta `X-Request-Id`; INFO para rechazos y validaciones, WARN para errores aguas arriba); `app/api/health/route.ts` (solo WARN `event=health outcome=degraded` cuando 503); `lib/pdf` (el `console.warn` actual pasa por `logEvent` como `event=pdf_render_failed` con `lang` y clase del error); `instrumentation.ts` en la raíz con `onRequestError` (ERROR `render_error` con `route_path`, `route_type`, `method`, `path` sin query, `digest`, clase del error; sin cabeceras ni mensaje) — **demuestra con un test de runtime en el standalone (W17) que `onRequestError` se ejecuta; si no, usa el fallback del plan (capturar en la propia página) y documéntalo**; test guardián `tests/log-gate.test.ts` (no hay `console.` fuera de `lib/log.ts`).
Tests: W1–W21 exactamente (extras anotados). Los tests de runtime usan el standalone real con la API falsa existente (`tests/helpers/standalone.ts` ya expone `log()`).
Reglas: las de `CLAUDE.md`/`AGENTS.md`/`docs/web-standards.md` de `cv-web` (el único `fetch` de cliente sigue siendo `lib/contact/client.ts`, `process.env` solo en `lib/api/config.ts`, repo PÚBLICO sin datos reales: los canarios son cadenas ficticias), sin git de escritura, sin duplicar código (reutiliza el transporte de `lib/api/request.ts`). No cambies comportamiento funcional ni respuestas salvo la cabecera `X-Request-Id`.
